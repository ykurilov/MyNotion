# Contract: Синхронизация v2 и файлы на сервере

Дополняет [001 sync-api](../../001-core-pages-editor/contracts/sync-api.md). Журнал пачек, снимки, устройства и коды ошибок — без изменений.

## Пачка `formatVersion: 2`

Расшифрованная пачка — как в 001, плюс:

### Поля блока

| field | value | Правило слияния |
|-------|-------|-----------------|
| `kindAndIndent` | `{kind, indent, linkedPageId}` — kind из нового списка (data-model.md) | позднее побеждает |
| `placement` | `{containerId: uuid\|null, sortKey}` | позднее побеждает; заменяет `sortKey` |
| `color` | `{text: цвет\|null, background: цвет\|null}` | позднее побеждает |
| `props` | объект по типу блока (data-model.md) | позднее побеждает; неизвестные ключи сохраняются |
| `text` | InlineText с новыми оформлениями | как 001: правки без знания друг о друге — «Две версии» |
| `isChecked`, `deleted`, `conflictResolved` | как 001 | как 001 |

Удаление строки или столбца таблицы, не видевшее правку ячейки (у ячейки `text.hlc` новее, чем знал удаливший), отменяется: строка или столбец возвращаются (research R3).

### Новая сущность `reminder`

`{"entity":"reminder","id":"<mentionId>","field":"doneAt","value":"<ISO>|null","hlc":"…"}` — позднее побеждает.

### Новые оформления в `text.runs`

`{"style":"textColor","color":"red"}`, `{"style":"backgroundColor","color":"yellow"}`, `{"style":"mention","pageId":"…"}`, `{"style":"date","date":{id,start,includesTime,timeZone,reminder}}`, `{"style":"equation","latex":"…"}`.

### Совместимость

- Mac с этой версией пишет только v2 и читает v1 и v2. `sortKey` из v1 — `placement` с прежним контейнером.
- Mac со старой версией пачку v2 не применяет: «Обновите MyNotion на этом Mac» (001); пачка ждёт.
- Снимок (`PUT /snapshot`) — тоже v2, с блоками всех потоков, `reminder` и описаниями файлов (не самими файлами).

## Файлы на сервере

Сервер хранит зашифрованные части файлов и ничего не знает о блоках. Авторизация — `Bearer <deviceToken>`, как у всех запросов 001.

### Шифрование (на Mac)

- Ключ файла = HKDF-SHA256(ключ синхронизации, salt = id файла (16 байт), info = `mynotion-file-v1`), 256 бит.
- Части по 8 388 608 байт исходника (последняя короче). Часть = `nonce (12) ‖ шифротекст ‖ тег (16)`, ChaChaPoly.
- Проверяемые данные части: `id файла ‖ номер части (u32) ‖ число частей (u32)`.
- После расшифровки всех частей — сверка SHA-256 исходника с `AttachmentRef.sha256`.

### Эндпоинты

#### `GET /files/{fileId}`
`200 {"fileId","partCount","parts":[0,1,…],"complete":bool,"bytes":<int>}` — что уже лежит; `404` — ничего нет (ещё не начали отправку или стёрт).

#### `PUT /files/{fileId}/parts/{index}?count=<partCount>`
Тело — части как есть, `Content-Type: application/octet-stream`, не больше 8 МБ + 28 байт.
- `201` — записана; повтор той же части — `200` (безопасный повтор после обрыва).
- `count` должен совпадать у всех частей файла, `index < count`, иначе `400`.
- `413 too_large` — часть больше предела; `409 file_complete` — файл уже собран и не меняется; `507 storage_full` — кончилась квота.
- Сервер пишет часть во временный файл и переименовывает после полной записи: оборванная часть не остаётся.

#### `POST /files/{fileId}/complete`
Тело `{"partCount":<int>}`. Все части на месте — `200 {"bytes":<int>}`, файл больше не меняется. Не хватает частей — `400 {"missing":[…]}`.

#### `GET /files/{fileId}/parts/{index}`
`200` — часть как есть (`application/octet-stream`); `404` — нет; `409 file_incomplete` — файл ещё не собран (части не отдаются, пока отправитель не закончил).

#### `DELETE /files/{fileId}`
`204`. Файл уходит в корзину сервера и стирается через 30 дней. Повтор — `204`. Файл в корзине для `GET` — `404`. Отправка части в файл из корзины достаёт его оттуда: прежние части стираются, файл собирается заново (Mac, вернувший блок со своей копией, просто отправляет его снова).

#### `GET /files/usage`
`200 {"usedBytes":<int>,"limitBytes":<int>,"files":<int>}` — для «Настройки → Синхронизация».

### Ошибки

Те же `{"error","message"}` 001, новые коды: `file_complete` (409), `file_incomplete` (409), `storage_full` (507).

### Хранение на сервере

- `/data/files/<первые 2 знака id>/<id>/<index>.part` (id — UUID в нижнем регистре; сервер приводит регистр сам; файл не больше 13 частей, иначе `413`; временные файлы записи — `/data/files/.tmp`); учёт файлов — таблица `files (id, part_count, bytes, complete_at, deleted_at, created_at, updated_at)` (`updated_at` — время последней новой части, по нему стираются брошенные загрузки) в той же SQLite.
- Квота — переменная `FILES_LIMIT_GB` (по умолчанию 50); считается по всем файлам, кроме стёртых из корзины.
- Корзина: раз в сутки стираются файлы с `deleted_at` старше 30 дней и несобранные файлы без новых частей 7 дней.
- Копии: к ежедневной копии базы (001) добавляется `backups/files-<дата>` — копия папки файлов жёсткими ссылками (`cp -al`), хранится 14 копий.
- Nginx: `client_max_body_size` не меньше 9 МБ (сейчас больше — ради снимков 200 МБ), тайм-аут чтения тела 120 с.

## Поведение Mac

- Отправка: части по одной, повтор с первой отсутствующей (`GET /files/{id}`), затем `complete`. Пачка с блоком не ждёт файла.
- Скачивание: очередь по одному файлу; файлы открытой страницы — в начало; `409 file_incomplete` или `404` — повтор через 1, 2, 4 … 60 мин; надпись на заглушке — «Ждёт отправки с другого Mac».
- Квота: `507` — сообщение в значке синхронизации «На сервере кончилось место для файлов», повтор раз в час; файл не теряется.
- Стирание: только сирота старше 30 дней, когда все устройства знают удаление (сборщик надгробий 001) — затем `DELETE /files/{id}` и стирание копии на Mac.
- Выключение синхронизации файлы на Mac не трогает (FR-024 001).
